# 실험 설계 (Experiment Design)

**IoT/AI 텔레메트리 파이프라인의 Edge→Cloud 구간에서 REST · gRPC · gRPC over QUIC 비교**

> 이 문서는 **논문의 방법론(Methodology) 절을 쓰기 위한 원본**입니다.
> 설치와 실행 방법은 [`SETUP_AND_USAGE.md`](SETUP_AND_USAGE.md)를 보세요.

---

## 1. 연구 질문

Edge Gateway는 이기종 센서에서 올라오는 측정값을 집계해, AI 에이전트에 공급하는
Cloud Gateway로 전달합니다. 센서 유형(온도, 습도, 기상, 대기질)은 서로 독립적인
작업이므로, 게이트웨이는 이들을 **동시 논리 스트림으로 분리**해 전송합니다.

> 손실이 있는 WAN 구간에서, 이 스트림들을 TCP 대신 QUIC으로 실어 나르면
> 클라우드의 AI 에이전트가 **실제로 받아보는 텔레메트리**가 측정 가능한 수준으로
> 달라지는가? 달라진다면 그 이득은 QUIC 자체의 것인가, HTTP/3 매핑의 것인가?

### 가설

N개 논리 스트림을 **순서 보장 TCP 바이트스트림 하나**에 다중화하면(gRPC over
HTTP/2) 스트림들의 운명이 묶입니다. 세그먼트 하나가 유실되면 커널이 그 구멍
너머의 바이트를 애플리케이션에 올려주지 않으므로, 재전송이 완료될 때까지
**모든 스트림이 함께 멈춥니다.** QUIC은 스트림별로 번호를 매기고 독립적으로
복구하므로, 실제로 데이터를 잃은 스트림만 멈춰야 합니다. 이 효과는 무손실
환경에서는 관측되지 않고, 손실률에 따라 커져야 합니다.

### 왜 "손실"과 "멀티스트림"은 두 축이 아니라 하나인가

Head-of-Line 블로킹은 깨끗한 링크에서는 **관측 가능한 결과가 없습니다.**
0% 손실에서는 모든 전송이 순서대로 회선 속도로 전달하고, 멀티스트림 처리량
비교는 대부분 라이브러리 오버헤드를 재게 됩니다. 블로킹은 **막힐 대상**이 있을
때에만 드러납니다.

따라서 이 실험은 "멀티플렉싱"과 "오류 복원력" 중 하나를 고르지 않고 **교차**
시킵니다. 스트림 수를 8개로 고정하고 손실률을 스윕합니다. 이 결정 하나가
한계적인 결과를 논문이 보여줄 수 있는 **메커니즘**으로 바꿉니다.

## 2. 아키텍처 대응 관계

```
┌ Cloud ─────────────────────────────────────────────────────────────┐
│  AI Agent / Cloud server                                           │
│              │ JSON-RPC 2.0                             [미구현]   │
│  Cloud Gateway  ── cmd/cloudgw ───────────────────────── [측정]    │
└──────────────┼─────────────────────────────────────────────────────┘
               │ REST | gRPC | gRPC over QUIC          ◀── 측정 대상 구간
┌ Edge ────────┼─────────────────────────────────────────────────────┐
│  Edge Gateway  ── cmd/edgegw ─────────────────────────── [측정]    │
└──────────────┼─────────────────────────────────────────────────────┘
               │ CoAP / MQTT
┌ Terminal ────┼─────────────────────────────────────────────────────┐
│  센서들     ── internal/sensor (인프로세스 생성기) ────── [모델링]  │
└────────────────────────────────────────────────────────────────────┘
```

Terminal 계층은 실제 MQTT 브로커나 CoAP 서버가 아니라 **결정론적 인프로세스
생성기**입니다. 이것은 지름길이 아니라 **통제 변인**입니다. 경로 위에 브로커가
있으면 큐잉·재시도·스케줄링 변동이 끼어드는데, 이는 Edge→Cloud 전송 계층과
아무 관련이 없으면서도 4개 arm이 서로 다르게 나오는 원인이 됩니다. 생성기는
링크가 볼 수 있는 모든 것(메시지 수, 크기, 카디널리티, 종류별 스트림 분리,
타이밍)을 보존하면서 그 변동만 제거합니다.

Cloud→AI Agent의 JSON-RPC 구간도 범위 밖이며, Cloud Gateway가 RPC를 종단하고
응답합니다.

> **논문에는 이렇게 쓰세요**: "단말 계층은 Edge Gateway에 병치된 합성 생성기로
> 에뮬레이션하였으며, 측정 구간은 Edge→Cloud 게이트웨이 홉이다."

## 3. 비교 대상 4종

| arm | 전송 계층 | 멀티플렉싱 | 페이로드 |
|---|---|---|---|
| `rest` | HTTP/1.1 + TLS 1.3 over TCP | 없음 — **스트림당 TCP 연결 1개** | JSON |
| `grpc` | gRPC over HTTP/2 + TLS 1.3 over TCP | N 스트림 → **TCP 연결 1개** | protobuf |
| `h3` | gRPC 프레이밍 over HTTP/3 (QUIC) | N 스트림 → QUIC 연결 1개 | protobuf |
| `qtun` | gRPC 프레이밍 on **raw QUIC 스트림** (HTTP 계층 없음) | N 스트림 → QUIC 연결 1개 | protobuf |

### 왜 QUIC arm이 두 개인가

`grpc-go`는 HTTP/3를 지원하지 않습니다. 따라서 "gRPC over QUIC"은 잘 정의된
단일 실체가 아니라 **직접 만들어야 하는 것**입니다. 한 가지만 만들면 결과가
모호해집니다. HTTP/2 대비 이득이 QUIC의 독립 스트림 복구 덕분인지, 아니면 단지
HTTP/3의 프레이밍·QPACK·컨트롤 스트림이 다른 코드이기 때문인지 구분할 수
없습니다.

둘 다 돌리면 해소됩니다.

- `h3` = **표준 경로**. gRPC 프레이밍을 그대로 두고 HTTP/3 매핑으로 나릅니다.
  실제 서비스가 채택할 만한 형태입니다.
- `qtun` = **메커니즘 분리**. 동일한 프레이밍을 QUIC 양방향 스트림에 직접
  올립니다. 전송 계층 효과를 가장 깨끗하게 읽는 방법입니다.
- **`h3`와 `qtun`의 격차가 곧 HTTP/3 매핑 비용**입니다. 세 번째 결과를 공짜로
  얻습니다.

### arm 간 비교 가능성을 보장하는 통제

1. **동일한 프레이밍.** gRPC 계열 3종 모두 gRPC 길이-프리픽스 메시지 포맷
   (1바이트 압축 플래그 + 4바이트 빅엔디언 길이)을 사용합니다. 캐리어만 다릅니다.
2. **동일한 코덱.** 3종 모두 같은 생성기가 만든 같은 protobuf 메시지를 인코딩합니다.
3. **동일한 페이싱.** 모든 arm이 같은 수의 논리 스트림을 열고, 같은 배치를 보내고,
   같은 수의 배치를 in-flight로 허용합니다.
4. **전 구간 TLS 1.3.** QUIC은 TLS 1.3을 강제하므로, TCP arm을 평문으로 돌리면
   부당한 이점을 주게 됩니다. 4개 arm 모두 같은 인증서, 같은 버전입니다.
5. **압축 전면 비활성화.** 와이어 바이트가 코덱이 만든 그대로이므로 바이트
   회계가 정직합니다.

### 논문에 반드시 명시할 한계

gRPC arm은 `grpc-go` 라이브러리가 아니라, Go 표준 `net/http` 위에 구현한
**와이어 호환 구현**입니다(실제 gRPC 경로·content-type·프레이밍·트레일러 사용).
이것은 의도적인 선택입니다. HTTP/2·HTTP/3·raw QUIC 세 arm에서 프레이밍과 코덱을
고정할 수 있는 유일한 방법이며, 그래야 arm 간 차이를 "라이브러리가 세 개라서"로
돌릴 수 없습니다. HTTP/2 arm의 캡처는 Wireshark에서 gRPC로 디코딩됩니다.

리뷰어가 `grpc-go`를 요구하면 다섯 번째 arm으로 추가해 `grpc`와 나란히 보고
하세요. 둘의 차이가 라이브러리 오버헤드를 정량화하며, QUIC 비교에는 영향을
주지 않습니다.

### REST를 허수아비로 만들지 않았다

HTTP/1.1은 실제로 다중화가 불가능하므로, REST arm에는 **스트림당 전용 TCP
연결**을 부여했습니다(처리량 레짐에서는 스트림당 `--inflight`개). 이것이 REST
텔레메트리 게이트웨이의 실제 배포 형태이며, **REST에 가장 유리한** 구성입니다.
연결별로 격리되므로 REST 역시 교차 스트림 HoL 블로킹을 겪지 않습니다. 대신
치르는 대가는 N번의 핸드셰이크, N개의 혼잡 제어 인스턴스, 그리고 JSON
오버헤드입니다 — 이것이 논문이 보고해야 할 트레이드오프입니다.

## 4. 네트워크 모델

```
c0 (Edge GW) ──1ms/1Gb──▶ r0 ──18ms/50Mb──▶ r1 ──1ms/1Gb──▶ s0 (Cloud GW)
                                   ▲
                            netem 손실 주입 (양방향)
```

- **기본 RTT ≈ 40 ms** (편도 20 ms): 현실적인 광역 edge-to-cloud 경로
- **병목 50 Mbit/s** (방향당), 액세스 링크는 사실상 무제한이라 병목이 명확
- **라우터는 IP 포워딩을 켠 Mininet 호스트**입니다(스위치가 아님). GAIA의
  `Generic` 토폴로지 모델을 따르며, 실제 2홉 라우팅 경로임을 논문에 명시할 가치가
  있습니다.

### 버퍼 크기 — 왜 이 값인가

GAIA에서 `queue_size`는 패킷 개수가 아니라 **큐잉 지연으로 환산되는 값**이며,
실제 `tbf` 버퍼는 `1×링크 BDP + 그 큐잉 지연`이 됩니다. 현재 설정
(18 ms / 50 Mbps / `queue_size=100`)은 다음을 만듭니다.

| 항목 | 값 |
|---|---|
| 링크 BDP | 150 패킷 (225 kB) |
| 추가 큐잉 지연 | 22 ms |
| 실제 버퍼 | 362 kB ≈ 242 패킷 (링크 BDP의 약 1.6배) |
| 버퍼 포화 시 RTT | 62 ms |

이 값은 두 실패 사이에서 의도적으로 잡은 것입니다. **버퍼가 얕으면** 큐
오버플로 드롭이 발생해 우리가 주입한 netem 손실과 섞이고, 그러면 "손실률 1%에서의
거동"이라는 실험 자체가 무의미해집니다. **버퍼가 깊으면** 버퍼블로트로 파이프라인
레짐의 지연이 부풀어 오릅니다.

> `python3 scripts/gen_scenarios.py --explain`이 현재 상수로부터 이 표를 그대로
> 계산해 출력합니다. 링크 파라미터를 바꾸면 반드시 다시 확인하세요.

### 손실 스윕

**0, 0.5, 1, 2, 5 %.** netem은 WAN 링크의 **양방향에** 설치되므로, 설정값 p는
각 방향에 p%를 의미하고 왕복 기준 손실 확률은 `1 - (1-p)²`입니다(1% → 1.99%).
논문에는 설정값과 왕복 환산값을 함께 적는 편이 정확합니다.

0% 행은 **대조군**이며, 4개 arm이 스톨 지표에서 서로 오차 범위 안에 있어야
합니다. 그렇지 않다면 전송 계층이 아니라 측정 하네스가 잘못된 것입니다.

## 5. 부하 모델

8종 센서, 각각 논리 스트림 1개:

`temperature`, `humidity`, `pressure`, `wind_speed`, `rainfall`, `co2`,
`pm25`, `illuminance`

각 스트림은 정규화된 `Measurement`들의 `Batch`를 보내고, Cloud Gateway는 배치당
`Ack` 하나를 돌려줍니다. 값은 센서 종류별 일주기 사인파에 가우시안 잡음을 더한
것이며, 스트림별로 시드가 고정되어 **재현 가능**합니다.

### 두 가지 레짐

| 레짐 | 배치 | in-flight | 무엇을 분리하는가 |
|---|---|---|---|
| `hol` | 측정값 20개 | 스트림당 1 | 클로즈드 루프. 처리량이 RTT에 묶여 **설계상** arm 간에 비슷해지므로, 차이가 나는 것은 "스트림이 얼마나 오래 막혀 있었나"뿐입니다. 지연·블로킹 실험. |
| `tput` | 측정값 100개 | 스트림당 8 | 파이프라인, 링크 포화. 혼잡 제어와 손실 복구가 지배합니다. 처리량 실험. |

둘 다 돌리는 것이 중요합니다. 한 레짐만 쓰면 "결과가 인가 부하의 부산물"이라는
반박을 부릅니다.

## 6. 측정 지표

Mininet 노드는 호스트 커널의 시계를 공유하므로 클라이언트와 서버 타임스탬프를
직접 비교할 수 있습니다. 덕분에 왕복뿐 아니라 **실제 편도 지연**을 보고합니다.
드문 일이므로 논문에 한 문장 할애할 가치가 있습니다.

### 일반 지표

| 지표 | 정의 |
|---|---|
| `goodput_mbps` | 초당 프레이밍된 애플리케이션 바이트. TLS·HTTP 헤더·QUIC 패킷 오버헤드는 **모든 arm에서 동일하게** 제외 |
| `messages_per_s` | 초당 전달·확인된 측정값 수. 텔레메트리를 소비하는 AI 에이전트가 실제로 신경 쓰는 값은 Mbps가 아니라 이것 |
| `bytes_per_msg` | 페이로드 효율. protobuf 대 JSON 차이를 직접 보고 |
| `rtt_p50/p90/p99/max_ms` | 배치 왕복 시간 |
| `oneway_p50/p99_ms` | 클라이언트 송신 → 서버 도착 |

### Head-of-Line 블로킹 증거

실행 구간을 100 ms 버킷으로 나눕니다. 어떤 버킷에서 배치를 하나도 완료하지 못한
스트림을 **스톨(stalled)** 상태로 봅니다.

**`stall_correlation`** — "적어도 하나가 스톨한 버킷" 중 "**모든** 스트림이
스톨한 버킷"의 비율.

```
stall_correlation = |{b : N개 스트림 전부가 b에서 스톨}|
                  / |{b : 최소 1개 스트림이 b에서 스톨}|
```

순서 보장 바이트스트림을 공유하면 이 값이 **1.0**으로 밀려갑니다 — 하나가
멈추면 전부 멈춥니다. 독립 스트림이면 **1/N** 근처에 머뭅니다. 메커니즘을
진술하는 단일 숫자입니다.

**`mean_stalled_streams`** — 스톨 버킷에 한정한, 동시에 멈춘 스트림 수의 평균.
스트림 수 N과 함께 보고하여 완전 격리(=1)로부터의 거리를 볼 수 있게 합니다.

**`p99_spread_ms`** — 스트림별 p99의 최댓값 − 최솟값. 공유 블로킹은 이 값을
0으로 압축하고(모두가 똑같이 고통받음), 스트림 격리는 벌립니다(운 나쁜 스트림만
고통받음). 유용한 교차 검증입니다 — `stall_correlation`과 **반대 방향**으로
움직이므로, 둘을 함께 보면 측정 아티팩트로 설명하기 어렵습니다.

**`timeline`** — 버킷별 스트림별 완료 수. fig4가 그리는 자료입니다. 이 그림은
요약이 아니라 **메커니즘 자체**를 보여줍니다. HTTP/2에서는 창백한 빈칸이 8개
스트림에 걸쳐 수직으로 정렬되고, QUIC에서는 흩어집니다.

## 7. 실험 매트릭스

```
손실 5단계 × 전송 4종 × 레짐 2종 × 반복 3회 = 120 run
```

run당 약 45초에 Mininet 구성·해제 시간을 더하면 전체 스윕은 대략 **2~2.5시간**
입니다. 반복은 **중앙값**으로 집계하며(한 run이 호스트 스케줄링으로 교란되어도
견딤), 그림에는 최소–최대 수염을 그려 산포를 숨기지 않습니다.

빠르게 줄이려면 `REPEATS=1`, 또는
`gen_scenarios.py --modes grpc,h3 --losses 0,1,5`로 좁히세요.

## 8. 타당성 위협과 대응

| 위협 | 대응 |
|---|---|
| 라이브러리 차이가 전송 계층 차이로 위장 | gRPC arm 전체에 단일 프레이밍·단일 코덱 적용. `qtun`이 QUIC을 HTTP/3로부터 분리 |
| TLS 비대칭 | 전 arm TLS 1.3, 동일 인증서 |
| 손실이 아니라 흐름 제어가 QUIC을 제한 | QUIC 수신 윈도를 BDP보다 훨씬 크게 설정 |
| 버퍼 오버플로 드롭이 주입 손실과 혼동 | 버퍼를 1×BDP + 22 ms로 설정, `--explain`으로 검증 |
| 핸드셰이크 비용이 첫 배치에 계상 | 측정 시작 전에 연결·스트림 개설 완료, 5초 워밍업 제외 |
| 호스트 스케줄링 잡음 | 3회 반복, 중앙값 집계, 최소–최대 수염 |
| 클라이언트 GC 일시정지가 네트워크 지연으로 보임 | 생성기 버퍼 재사용, 배치당 할당 프로파일 평탄 |
| 유저스페이스 QUIC 대 커널 TCP의 CPU 비대칭 | **통제 안 됨 — 명시할 것.** quic-go는 유저스페이스에서 패킷마다 시스템 콜을 하고 TCP는 커널에서 돕니다. CPU 병목 호스트에서는 **TCP에 유리**하므로 QUIC의 승리는 보수적 추정이고, 0% 손실에서 QUIC이 지면 프로토콜이 아니라 이 효과일 수 있습니다. 실행 중 호스트 CPU를 기록하고 그렇게 서술하세요. |
| netem 손실이 균등·독립 분포 | 실제 손실은 버스트성. 한계로 명시하고, `netem loss gemodel` 후속 실험을 자연스러운 확장으로 제시 |
| 단일 클라이언트, 단일 경로 | 확장성·다중 경로에 대해서는 결론을 내지 않음 |

## 9. 예상 결과와 해석

0% 손실에서는 4개 arm이 지연과 스톨 지표에서 서로 가까워야 합니다.
`grpc`/`h3`/`qtun`은 순전히 protobuf 대 JSON 때문에 `messages_per_s`와
`bytes_per_msg`에서 `rest`를 앞서야 합니다. 이 행이 정합성 점검입니다.

손실이 올라가면 꼬리 지연과 stall correlation의 예상 순서는 다음과 같습니다.

```
grpc  (최악 — TCP 스트림 공유, 스톨 공유)
rest  (N개 연결이라 교차 스트림 블로킹은 없으나, N개 혼잡 윈도 + JSON 오버헤드)
h3    (독립 QUIC 스트림 + HTTP/3 매핑 비용)
qtun  (최선 — 독립 QUIC 스트림, HTTP 계층 없음)
```

### `grpc`가 QUIC arm과 분리되지 않는다면

논문에 쓰기 전에 **반드시** 확인하세요. 8개 스트림이 정말로 TCP 연결 하나를
공유했는지 봐야 합니다. 실행 중 c0 네임스페이스에서 `ss -tin`을 돌리면 gRPC
포트로 established 연결이 **정확히 1개**여야 합니다. `edgegw`는 HTTP/2 협상
실패 시 즉시 중단하지만, 스트림 한계 압력으로 두 번째 연결이 열리면 측정하려던
효과가 조용히 사라집니다.

### 이 자료가 뒷받침하는 주장

- 전송 계층의 스트림 독립성은, 다중 유형 IoT 텔레메트리에서 손실 환경의 꼬리
  지연과 교차 스트림 스톨을 줄인다.
- 그 효과는 깨끗한 링크에서는 무시할 만하고 손실률에 따라 커진다.
- 이득의 대부분은 HTTP/3가 아니라 QUIC의 것이다(`h3` 대 `qtun` 격차로부터).
- protobuf 대 JSON은 별개의, 가산적인, 손실과 무관한 이득이다.

### 뒷받침하지 **않는** 주장

확장성, 다중 클라이언트, 이동성, 연결 마이그레이션, 0-RTT, 버스트/상관 손실.
이들은 향후 과제입니다.
